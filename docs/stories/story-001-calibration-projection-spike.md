# Story 001: Calibration Projection Spike

## Goal

Prove that a rough laptop-as-gateway + HDMI projector + fixed camera rig can project a source grid onto a real 1-inch battle mat accurately and quickly enough to be useful at the table.

## Background

The first hardware path does not assume a dedicated USB webcam. An iPhone can act as a remote camera fixed to the projector with a temporary cardboard or printed mount. The likely finished home rig uses a cheap webcam fixed to the projector and plugged into a Raspberry Pi or similar mini-computer. This keeps the camera/projector relationship repeatable while still requiring per-placement calibration against the physical mat.

This story intentionally does not require remote storage/auth, native iOS, AI cleanup, map libraries, or app polish.

Scout 001 identified Mappadux / Dynamic Map Renderer v2 as close prior art for QR pairing, local web projection, fog, and true-table-scale rendering. Before building the projection UI from scratch, this story should run a short Mappadux spike to decide whether to fork/adapt the codebase, borrow specific projection/scaling concepts, or proceed independently.

## Scope

Build the smallest experiment that can:

- inspect Mappadux's projector, pairing, and scaled-view architecture against this story's camera-calibrated projection needs,
- show a calibration pattern through the projector,
- capture the battle mat and projected pattern through the fixed camera feed,
- manually or semi-automatically identify the mat grid,
- compute a planar transform from desired mat coordinates to projector pixels,
- project a test grid aligned to the physical mat,
- support manual nudge, scale, and rotation correction.

## Acceptance Criteria

- A real or printed 1-inch grid can be used as the calibration target.
- A source grid can be projected so 5 ft squares align 1:1 with physical squares.
- A 10 ft source-grid mode can project each source square as 2 by 2 physical squares.
- The projected grid can be nudged, scaled, and rotated without restarting the whole flow.
- The test records approximate alignment error in inches or fractions of a mat square.
- The test records setup time from starting calibration to useful projection.
- The test records camera/projector placement notes and any failure modes.
- The test records whether Mappadux should be forked/adapted, used as implementation reference only, or rejected for this product.
- The result is good enough to decide whether the next story should improve calibration, projection display, source-map normalization, UI controls, or hardware selection.

## Non-Goals

- Full phone controller UI.
- Polished map import.
- Remote storage/auth.
- Native iOS app.
- AI Auto-Clean.
- Inpainting or Clean/Hide Pen.
- Saved map library.
- Automatic perfect grid detection.

## Current Mappadux Decision

Use Mappadux as implementation reference only for Story 001. Borrow concepts around a separate projector view, true-table-scale thinking, static/PWA viability, local storage, and future QR/pairing. Do not fork or adapt it yet because its architecture is optimized for a broad VTT-at-home workflow and does not solve this story's fixed camera/projector homography against a real mat.

Several candidates are plausible interior grid patches rather than the whole mat extent, with low lattice scores between `0.02` and `0.08`. These overlays are useful triage inputs, but they are not accuracy evidence until the real-home fixtures are manually labeled and scored.
- The 8 real-home mat photos are now manually labeled and benchmarkable. A scored OpenCV run with `npm run benchmark:opencv-real-home` produced 0/8 strict real-camera proxy successes, 0 manual seeds, 0 rough seeds, 8 safe refusals, 0 wrong-confident results, and 0 benchmark errors. Artifacts are in `test-results/story-001-real-home-opencv-scored/`. All 8 real-home labels use extrapolated/off-image ground-truth corners, and the current candidate pools produced no exact row/column candidates. This is the first real-camera proxy baseline, not a product failure verdict.
- Real-camera scoring should not treat the manually labeled outer quadrilateral as the only valid truth. The labels express the visible, usable grid region by human judgment. Detector evaluation should also consider interior lattice pitch/orientation, visible-grid overlap, conservative versus expansive extent mismatch, and whether a candidate is a useful editable seed despite imperfect outer extent. Wrong lattice ownership remains a hard failure.
- Slight camera lens distortion may be hurting line detection, but the current real-home run mainly shows extent and lattice-ownership failure. Camera undistortion, active projected calibration, fiducials, or denser projector-camera mapping should be scouted if real-camera evidence continues to show curved-line or homography-limit failures.
- Added an optional AI-assisted grid-evidence recipe in `docs/evals/ai-grid-current-recipe.md`. The current best remote candidate uses Grok white gridline masks plus adaptive dots-only intersection masks, then local deterministic dot-lattice fitting. It re-scores with `npm run benchmark:ai-grid-current` and currently produces 8 accepted visible-lattice geometries on the 8 real-home proxy photos when allowed to retry dots up to the adaptive-eight policy. Generated red/blue axis-color masks are not trusted for horizontal/vertical metadata because the colors can drift within the same physical line family.
- The current AI-grid benchmark now reports a `parallel_wave3_then2` speed policy: white-line mask plus three dots-only samples in parallel, followed by two more dot samples only if the first wave has no accepted geometry. On the current artifact set it keeps 8/8 accepted visible-lattice geometries, uses 26 total dots-only calls, and estimates about 9.8 seconds average wall-clock before local fitting. An economy policy, `parallel_wave2_then1_then2`, keeps 8/8 accepted with 21 dots-only calls but estimates about 12.7 seconds average wall-clock. Live runner checks confirm the tradeoff: the hard `real-map-home-IMG_9719.jpg` accepted in 15.933 seconds with the speed schedule and 30.061 seconds with the economy schedule; the easy `real-map-home-IMG_9722.jpg` accepted in 7.625 seconds with the economy schedule after two dot samples. Line-only challengers were tested but not promoted: `npm run benchmark:ai-line-junction` produced 4 candidate geometries and 4 refusals, `npm run benchmark:ai-line-lattice` produced 2 candidates and 6 refusals, and `npm run benchmark:ai-family-stripes` produced 0/16 usable stripe-family seeds.
- The AI-grid scorer now separates geometry decision from projection readiness. `accepted-visible-lattice-geometry` means a visible lattice was found; it does not by itself mean full-span projection is safe. Reports now distinguish label-backed benchmark readiness from `noLabelProjectionReadiness`, which uses only fit metrics, observed mesh support, early-return safety, and ambiguity flags. On the current guarded risk-aware replay the benchmark says 7/8 full-span auto candidates, while no-label readiness says 4/8 full-span auto, 3/8 manual extent check, and 1/8 observed-region candidate, with 0 dangerous no-label-auto disagreements against benchmark readiness.
- A stronger no-extra-AI-call line parser now exists: `npm run benchmark:ai-line-skeleton` skeletonizes the white-line mask and extracts branch-point junctions. It produced 3 accepted visible geometries, 2 candidates, and 3 refusals on the 8 real-home proxy photos. `npm run benchmark:ai-family-pair` directly tested the paired one-family line-mask idea and produced 1 accepted visible geometry, 4 candidates, and 3 refusals. These results keep the line approach alive as a lower-cost/manual-seed helper, but the current 8/8 recipe remains white-line plus dot consensus.
- Added `npm run benchmark:ai-grid-parallel-hybrid` as an experimental balanced policy: first wave is the white-line mask plus two dot samples, a skeletonized line-mask accept gate can stop before the fallback wave, and the fallback wave launches three more dot samples. Replayed artifacts estimate 8/8 accepted with 21 dots-only calls, about 11.0 seconds average wall-clock, and 19.3 seconds max. A fresh live run on `real-map-home-IMG_9717.jpg` did not reproduce the skeleton early accept; it fell back to dot consensus and accepted in 24.458 seconds after 5 dot samples. Keep this as experimental economy/prep evidence, not the live-table default.
- Prompt challengers on hard `real-map-home-IMG_9719.jpg` did not improve the optional AI path: `white-intersection-centroids-v2` matched only 17/867 visible intersections, and `pink-overlay-visible-v1` scored weaker foreground alignment than the current white-line mask.
- Added a synthetic active-calibration simulation with `npm run benchmark:active-fiducial-sim`. It compares known-ID projected ArUco markers, symmetric/asymmetric projected circle grids, projected ChArUco, one-frame composite fiducial/circle patterns, static two-frame fiducial-plus-circle refinement, and target-adapted two-frame fiducial-plus-surface-circle refinement under the same randomized camera/projector geometry, then solves projector-to-camera homography with RANSAC and full-surface holdout metrics. The expanded run `npm run benchmark:active-fiducial-sim -- --trials 240 --seed 20260531` now makes one-frame perimeter fiducials plus interior circles the leading synthetic candidate: 240/240 accepted, 0.071 px median p95 feature error, and 0.086 px median p95 surface error after masking detected marker regions before circle detection. The previous best target-adapted two-frame hybrid also stayed robust at 240/240 accepted with 0.133 px feature / 0.174 px surface error. ChArUco is a mature fallback but was weaker in the expanded run at 239/240 accepted with 0.186 px feature / 0.385 px surface error. The harness also includes point-level lens and projector distortion stress checks: known camera undistortion improved raw-vs-truth p95 from 3.341 px to 0.102 px, and projector-distortion stress moved from 21.512 px raw commanded-pixel surface p95, to 7.778 px with residual mesh, to 0.090 px with known projector compensation. Photometric preflight stress accepted 240/240 before and after black/white normalization, but normalization improved feature p95 from 0.181 px to 0.115 px and surface p95 from 0.420 px to 0.315 px, so it is optional accuracy hardening rather than a required live default. This is not physical proof, but it makes Scout 003's active-calibration branch concrete: the physical pass should try the one-frame perimeter fiducial/interior-circle pattern first, then compare ChArUco, plain fiducials, asymmetric circles, and target-adapted two-frame refinement under real brightness, focus, exposure, and occlusion.
